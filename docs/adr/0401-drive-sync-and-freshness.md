# ADR 0401 — Google Drive sync and permission freshness

Status: Accepted for M4 (pending planning review). Relates to: FR-10, FR-02, roadmap "M4 and M5 connector and UI details", ADR 0301, ADR 0303.

## Context

Drive is an external system of record for sharing. The application can only know Drive's permissions as of its last read, and Drive offers no push revocation the laptop stack could rely on. The roadmap requires full, incremental, move, deletion and ACL sync, denial when permissions cannot be established, a 15-minute demo interval and a nightly interval otherwise, and a visible last verified sync time without promising immediate external revocation.

## Decision

1. **A source is a Drive folder** bound to one tenant and one owning department. The admin sets the attributes Drive does not carry (department, classification, department restriction, countries). Drive sharing supplies only layer 4 (resource grant) of the reference policy; the other four layers are unchanged.
2. **Every sync re-reads every file's permission list.** A run walks the folder tree breadth-first and reads each file's permissions. Content is downloaded only when the file's fingerprint changed (`md5Checksum`, or `modifiedTime` for Google-native files), so unchanged files are not re-ingested and an unchanged ACL does not rewrite grants (no policy-epoch churn). New files and new content use the M3 ingestion path unchanged (permissions saved before the job exists, staged generations, tombstones).
3. **Mapping.** A `user` permission grants the tenant user with that exact email. A `group` permission grants a tenant user only when **all three** hold in the current run:
   - the Google group email is explicitly linked to an internal group (`external_group_links`);
   - the user is a member of that internal group;
   - the user's **current Google membership was verified** (`list_group_members`).

   A link alone never establishes who belongs to a Google group. If membership cannot be verified (directory not enabled, an API error, a nested group, a member without an email), the group permission grants nobody and is recorded as `group_membership_unverified`.

   A verified member is stored in `drive_group_grants` (user, internal group, Google group email). That row is **not** a grant by itself. `load_resource_meta(s)` turns it into an allow only while the link from the Google group to the internal group still exists **and** the user is still in that internal group. So removing the internal membership, or unlinking the group, takes effect at the next authorization point without any Drive sync: a fresh question, the publication recheck of an active answer, citation reopen and replay. Both changes raise the policy epoch. Each run recomputes the rows, so a later run that cannot verify membership, or finds the user removed in Google, takes the access away, and a further successful run does not bring it back. Rows are keyed by Google group email too (migration 0010). If two Google groups are linked to the same internal group and both share the file, each grants access on its own: unlinking one keeps access through the other, and unlinking the last one denies at once. A direct user share on the same file is a separate grant and is unaffected. M3 upload grants to internal groups are unchanged.

   `domain` and "anyone with the link" grant nobody. Unmapped principals are recorded per item for the admin. Every Drive role from `reader` up implies read; Drive has no deny.
4. **Fail closed, three ways.**
   - The root or any folder cannot be listed, or credentials fail → the run fails, `permissions_current = false`, and **every** item of the source is denied until a later run succeeds.
   - One file's permission list cannot be read (403/404 or no list returned) → that item's resource becomes `permission_state = unknown` (denied); the rest of the source stays current.
   - Readers deny connector content once `last_verified_sync_at` is older than the tenant's `max_staleness_seconds` (30 minutes in demo mode, 30 hours nightly), whether or not a sync ever reported failure. This covers a stopped scheduler.
   A paused or deleted source, or a tenant that disabled the `google_drive` connector, also denies its content.
5. **One enforcement point.** `load_resource_meta(s)` computes `permissions_current` in SQL from the resource, its source and the tenant settings. Eligibility (search), `can_read`, publication rechecks, citation reopen and replay all go through it, so no path can serve Drive content the freshness rule denies.
6. **Verified time is conservative.** `last_verified_sync_at` is the run's *start* time: every permission was read after it.
7. **Moves and removals.** A rename or move inside the tree updates title and path and keeps the document. A file trashed, deleted or moved out of the tree is tombstoned (M3), and its Qdrant points are removed. If it reappears it becomes a new document; a tombstone is never resurrected.
8. **Schedule.** Celery beat asks PostgreSQL every minute which sources are due (`connector_sources_due`): demo — 15 minutes after the last start; nightly — once per day after 02:00 UTC. A lease on the source row makes duplicate deliveries no-ops. Admins can also sync on demand.
9. **Stale runs are fenced out.** A run holds the source through `claim_run_id` and records the source's `policy_version` at claim time. Every transaction that writes on the run's behalf first re-locks the source row (`SELECT … FOR UPDATE`) and requires both values to match. That covers item and grant writes, document creation and versions, tombstones, marking permissions current, and releasing the claim. An admin policy change (department, classification, restriction, countries, status) bumps `policy_version`, releases the claim and sets `permissions_current = false` (`access = resync_required`). A newer worker that takes over an expired lease replaces `claim_run_id`. Either way the older run ends `superseded`: it writes only its own run row and never touches the newer claim. Objects it already uploaded to storage are unreferenced and harmless.
10. **Sync requests are correlated, and redelivery is safe.** `POST …/sync` creates a `queued` run row and returns its id. The worker continues that row, or marks it `skipped` (for example `sync_in_progress`), so a caller waits for exactly its own run (`GET …/runs/{run}`). A Celery redelivery of the same run id is recognised under a row lock:
    - a terminal run reports its status and does no work;
    - a running run with a live lease is a duplicate and does no work;
    - a running run whose lease expired (the worker died) is recovered as the same run with `attempt + 1` and a new `claim_token`.

    When a *different* run claims the source (for example a scheduled run after a dead manual run's lease expired), every other run of that source still marked `running` is closed as `superseded` (`claim_taken_over`). So an abandoned run ends terminal even if it is never redelivered, and a late delivery of it does no work and leaves the newer result alone. The fence checks the claim token, so the dead attempt can no longer write. A superseded attempt updates the run row only where `attempt` still matches its own, so it never overwrites the recovered run. Work is not applied twice: items finished before the crash have matching fingerprints and are skipped.
11. **Upgrade fails closed (migration 0009).** Drive group grants from 0007 (unverified) and group-derived user grants from 0008 (not tied to internal membership) cannot be told apart from valid grants. The upgrade therefore removes group grants on connector resources, marks every source not current (`upgrade_resync_required`, shown as `resync_required`), and clears item permission fingerprints. Drive content is denied until a sync under the new rules rewrites every item. M3 upload resources are not touched.
12. **Credentials are the operator's.** `DRIVE_CONNECTOR_CONFIG` binds each tenant slug to server-side credentials (service account key file or OAuth refresh token, `drive.readonly`) and to the root folders that tenant may use. A tenant admin cannot point a source at a folder outside that list, so one deployment credential cannot leak another tenant's folder. The file is re-read on every use. Each run checks its root against the current list **before any Drive request**. A root the operator removed fails the run (`root_not_allowed`), and previously imported content of that source is denied from then on. Google group membership is trusted only when the operator sets `group_membership: "directory"` (Workspace Admin SDK, read-only member scope).

## Consequences

- External revocation is effective **after the next verified sync** (≤15 minutes in demo mode), and within the staleness bound at worst. The admin console shows the last verified sync time and the current access state of every source.
- A transient Drive outage denies a whole source until the next successful run. This is deliberate.
- Consumer Google accounts have no API for group membership. Without a Workspace directory, every Drive **group** share is unresolved, and only direct user shares grant access. This is the fail-closed behaviour the roadmap requires ("missing visibility must deny access").
- The full permission re-read costs one API call per file per run. That is acceptable for the project's small corpus and is what makes a run "verified". The Changes API could later reduce downloads further, but it cannot replace the full ACL read without weakening the verification claim.
